# Contributing to pycdc-rapid

## Reporting issues

An issue report must include:

- The affected `.pyc` file. Remove secrets first, but provide a minimized PYC that still reproduces the problem.
- The Python version that produced the PYC, including the implementation/version when it is not CPython.
- A clear problem description: command used, expected result, actual result, and whether the result crashes, warns, or produces incorrect source.
- Whether the report was reproduced with the latest `pycdc-rapid` commit or release.

Optionally include `pycdc`/`pycdas` stderr output, a disassembly, and the generated source. These are especially useful for stack, block, invalid-opcode, and marshal-read diagnostics.

## Submitting pull requests

Every pull request must include:

- A focused source test (`.py`) and the corresponding PYC generated by the intended Python version.
- The affected Python bytecode version(s), a concise description of the recovered behavior, and any known best-effort limitations.
- Build and verification commands, including `pycdas`, `pycdc`, and relevant syntax or round-trip checks when available.

For a large change to bytecode decoding, stack/block recovery, AST construction, or version support, the PR must also decompile every PYC currently in the project before submission. This includes tracked project fixtures and the four local PYC inputs used at the start of maintenance. Those four files are local test inputs only: do not copy them into repository PYC test directories or commit them. Report the command, exit-code summary, and any remaining diagnostics; do not hide known incomplete output.

Keep changes small and reviewable. Do not commit build directories, executables, object files, generated PYC files, decompiler output, or personal local files unless they are explicitly required as an approved test fixture.
